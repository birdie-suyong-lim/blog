> 작성일: 2026-08-06
> 참고: RFC 6265bis (Cookies: HTTP State Management Mechanism), web.dev "Schemeful Same-Site"

`http://app.example.com`과 `https://api.example.com`은 같은 사이트일까? 2021년 이전의 브라우저는 "그렇다"고 답했다. 지금의 브라우저는 "아니다"라고 답한다. **same-site 판정에 스킴(http/https)이 포함**되도록 정의가 바뀌었기 때문이다 — 이것이 Schemeful Same-Site다.

한 줄 요약처럼 보이는 이 변화는 세션 쿠키 인증을 쓰는 웹 개발 전반에 실질적인 파장을 만든다. 특히 "로컬 http 개발 서버에서 https API에 붙는" 흔한 개발 구성이 정확히 이 규칙에 걸린다. 이 글은 이 규칙이 **애초에 왜 존재하는지**부터, **어떤 메커니즘으로 동작하는지**, 그리고 **실무에서 어떤 함정으로 나타나는지** 순서로 정리한다.

---

## 1. 배경: 쿠키의 원죄와 SameSite의 탄생

### 쿠키는 "누가 보낸 요청인지" 가리지 않았다

쿠키의 원래 규칙은 단순하다. **요청이 어디로 가느냐만 보고, 어디서 출발했느냐는 보지 않는다.** `bank.example`의 세션 쿠키는 `bank.example`로 가는 모든 요청에 자동으로 실린다 — 그 요청을 만든 페이지가 `evil.example`이어도.

이 성질을 ambient authority(주변 권한)라고 부른다. 그리고 이것이 **CSRF(Cross-Site Request Forgery)** 공격의 토대다. 공격자 페이지가 몰래 만든 폼 제출이:

```html
<!-- evil.example 페이지 안 -->
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker" />
</form>
<script>document.forms[0].submit()</script>
```

피해자의 브라우저에서 실행되면, 브라우저는 성실하게 `bank.example`의 세션 쿠키를 실어 보낸다. 서버 입장에서는 로그인한 본인의 정상 요청과 구분할 수 없다.

### SameSite 속성: "출발지도 보자"

이 구멍을 막기 위해 쿠키에 `SameSite` 속성이 도입됐다(2016년경 Chrome 51부터, RFC 6265bis). 쿠키를 구울 때 서버가 선언한다:

| 값 | 의미 |
| --- | --- |
| `Strict` | 요청의 출발지와 도착지가 same-site일 때만 쿠키 전송. 외부 사이트에서 링크 타고 들어온 첫 내비게이션에도 안 실림 |
| `Lax` | 기본적으로 Strict와 같지만, **최상위 GET 내비게이션**(링크 클릭·주소창 이동)에는 예외적으로 실어줌 |
| `None` | 예전처럼 어디서 출발했든 전송. 단 `Secure`(https 전용)와 함께 써야만 유효 |

2020년 Chrome 80부터는 속성을 안 쓴 쿠키가 **기본값 `Lax`로 취급**되면서, SameSite는 옵트인이 아니라 웹의 기본 방어선이 됐다.

여기까지가 1막이다. 그런데 이 방어선의 핵심 개념인 "same-site"가 정확히 무엇인지가 다음 문제다.

---

## 2. site란 무엇인가: origin과 다르다

브라우저 보안에는 비슷해 보이는 두 단위가 있다.

- **origin** = `(스킴, 호스트, 포트)`. Same-Origin Policy의 기준. `https://a.example.com`과 `https://b.example.com`은 **다른** origin이다.
- **site** = 등록 가능 도메인(eTLD+1) 기준. `a.example.com`과 `b.example.com`은 둘 다 `example.com` 아래이므로 **같은** site다.

eTLD(effective TLD)는 `.com`, `.co.kr`, `.github.io`처럼 "그 아래에서 일반인이 도메인을 등록할 수 있는 접미사"다(Public Suffix List로 관리). eTLD+1은 거기에 한 단계를 더한 것 — `example.com`, `example.co.kr`, `username.github.io`가 각각 하나의 site다. 그래서 `a.github.io`와 `b.github.io`는 서로 다른 사용자의 사이트일 수 있으므로 **cross-site**다.

왜 쿠키는 origin이 아니라 이렇게 느슨한 site 단위를 쓸까? **서브도메인 간 협력이 웹의 오래된 관행**이기 때문이다. `sso.company.com`에서 로그인하고 `app.company.com`에서 그 세션을 쓰는 구조를 origin 단위로 판정하면 전부 부서진다. 포트를 안 보는 것도 같은 관용이다.

이 시점(2016~2020)의 site 정의에는 **스킴이 없었다.** `http://app.example.com`과 `https://api.example.com`은 same-site였다.

---

## 3. Schemeful Same-Site: 왜 스킴이 추가됐나

### 위협 모델: http는 네트워크 공격자의 것이다

스킴을 무시하는 판정에는 구조적 허점이 있다. **http는 암호화도 무결성 보장도 없다.** 같은 와이파이의 공격자, 경로 상의 중간자(MITM)는 http 응답을 마음대로 위조할 수 있다.

그러면 이런 시나리오가 성립한다. 회사가 모든 서비스를 https로 운영해도, 네트워크 공격자가 피해자의 브라우저에 `http://anything.example.com` 응답을 위조해 밀어 넣으면 — 스킴 무시 판정에서는 이 위조 페이지가 `https://bank.example.com`과 **same-site**다. 즉:

- 위조 http 페이지에서 https 서버로 보내는 요청에 `SameSite=Strict/Lax` 쿠키가 실린다 → **SameSite가 막으려던 CSRF가 부활**한다.
- 위조 http 페이지가 `Set-Cookie`로 site 전체에 쿠키를 심을 수도 있다 → 세션 고정(session fixation)류 공격의 통로가 된다.

정리하면, **사이트의 보안 수준이 가장 약한 스킴(http) 쪽으로 하향 평준화**되는 문제다. 서비스를 전부 https로 옮겨도, http라는 뒷문이 same-site 자격을 갖고 있는 한 SameSite 방어는 완성되지 않는다.

### 해법: site = (스킴, eTLD+1)

그래서 site의 정의 자체에 스킴을 넣었다. 이것이 Schemeful Same-Site이고, Chrome 89(2021년 3월)부터 기본 적용됐다. 이제 판정은:

| A | B | 판정 | 이유 |
| --- | --- | --- | --- |
| `https://a.example.com` | `https://b.example.com` | same-site | 스킴 일치, eTLD+1 일치 |
| `https://a.example.com` | `https://a.example.com:8443` | same-site | 포트는 안 본다 |
| `http://a.example.com` | `https://a.example.com` | **cross-site** | 같은 호스트여도 스킴 불일치 |
| `http://a.example.com` | `https://b.example.com` | **cross-site** | 스킴 불일치 |
| `https://a.example.com` | `https://localhost` | cross-site | eTLD+1 불일치 |

기억할 규칙은 하나다: **스킴은 본다, 포트는 안 본다, 서브도메인은 묶는다.**

### cross-site가 되면 실제로 일어나는 일

`SameSite=Lax`(기본값) 쿠키 기준으로, cross-site 컨텍스트에서는 두 방향이 모두 막힌다.

- **전송 차단**: cross-site XHR/fetch/서브리소스 요청에 쿠키가 실리지 않는다. `credentials: 'include'`(fetch), `withCredentials: true`(axios)를 아무리 선언해도 소용없다 — 그 설정은 "실어달라"는 요청일 뿐이고, 실을지는 브라우저의 SameSite 판정이 결정한다.
- **저장 차단**: cross-site 요청의 응답으로 내려온 `Set-Cookie`(Lax/Strict)는 브라우저가 저장을 거부한다.

유일한 예외는 Lax의 존재 이유인 **최상위 GET 내비게이션**(링크 클릭으로 페이지 자체가 이동하는 경우)뿐이다. SPA의 API 호출은 전부 XHR/fetch이므로 이 예외의 혜택을 받지 못한다.

## 4. 함정: 이론이 실무에서 발을 거는 지점들

### 함정 1 — "Secure만 만족하면 페이지가 http여도 된다"는 반쪽 지식

다음 명제는 참이다.

> 쿠키의 `Secure` 속성은 **요청 대상**이 https인지만 본다. API가 https라면, 페이지가 http여도 Secure 조건 자체는 통과한다.

여기서 "그러니까 로컬 개발 페이지는 http여도 무방하다"로 비약하기 쉽다. 하지만 `Secure`와 `SameSite`는 **서로 독립적인 두 개의 축**이다. Secure 축을 통과해도, http 페이지 ↔ https API는 schemeful 판정에서 cross-site가 되어 SameSite 축에서 막힌다. 참인 전제에서 출발한 반쪽 지식이라 그럴듯하고, 그래서 팀 문서에 한번 박제되면 오래 살아남는다.

### 함정 2 — 로컬 개발 환경이 정확히 이 케이스다

세션 쿠키(`SameSite=Lax`) 인증을 쓰는 서비스의 흔한 개발 구성:

- 프론트: `http://app-local.example.com:5173` (로컬 dev 서버, hosts 파일로 127.0.0.1 매핑)
- API: `https://api-dev.example.com` (배포된 개발 서버)

eTLD+1을 맞추려고 서브도메인 호스트까지 마련한 설계인데, **스킴이 다르므로 cross-site**다. 로그인 응답의 세션 쿠키는 저장이 거부되고, 이후 요청에도 실리지 않는다. 세션이 성립할 방법이 없다.

### 함정 3 — 증상이 "로그인 성공"으로 위장한다

이 문제가 오래 잡히지 않는 이유는 증상이 교묘해서다.

- **로그인 요청 자체는 쿠키가 필요 없다.** 자격증명은 요청 본문으로 가므로 200이 떨어진다.
- **SPA는 로그인 응답 본문만으로 화면을 전환한다.** 쿠키가 조용히 버려져도 알아챌 계기가 없다.
- 처음 실패하는 것은 **로그인 다음의** 요청이다. 그래서 원인을 "로그인 이후의 무언가"(토큰 로직, 계정 상태)에서 찾게 된다.

덤으로, 서버 프레임워크에 따라(예: Spring Security) CSRF 검증 필터가 인증 확인보다 앞에 있어서 **세션 없는 POST가 401이 아니라 403 CSRF 오류로 응답**되기도 한다. "세션이 없다"는 본질이 "CSRF 토큰이 잘못됐다"는 메시지로 한 번 더 위장되는 것이다.

### 함정 4 — origin 지식과의 혼선

Same-Origin Policy에 익숙하면 "포트가 다르면 다르다"가 몸에 배어 있고, SameSite의 옛 정의에 익숙하면 "스킴은 안 본다"가 배어 있다. 현재 규칙은 그 중간이다 — 포트는 안 보고 스킴은 본다. CORS 허용 오리진 목록(스킴+호스트+포트를 전부 비교)과 SameSite 판정(스킴+eTLD+1)이 서로 다른 기준이라는 점도 디버깅 때 혼선을 만든다. CORS를 통과했는데 쿠키가 없을 수도 있고, 쿠키는 될 조합인데 CORS에서 막힐 수도 있다.

## 5. 진단: 30초 판별법

세션 인증이 "반쯤 되는" 증상을 만나면 이 순서로 확인한다.

1. **로그인 직후 콘솔에서 세션 확인 API 호출**
   ```js
   await fetch('https://api-dev.example.com/api/v1/auth/me', { credentials: 'include' })
   ```
   방금 로그인했는데 401이면 토큰/CSRF 로직이 아니라 쿠키 문제다.
2. **DevTools > Application > Cookies**에서 API 도메인의 세션 쿠키 존재 확인. 없으면 저장부터 거부된 것이다. (Network 패널 응답에는 `Set-Cookie`가 보이는데 저장은 안 돼 있는 것이 전형적인 모습이다 — 헤더 옆 경고 아이콘에 차단 사유가 뜬다.)
3. **주소창 스킴 확인.** 페이지가 `http://`, API가 `https://`면 그것이 원인이다.

## 6. 해법: 스킴을 맞춘다

근본 해결은 하나다 — **로컬 개발도 https로 통일**한다. [mkcert](https://github.com/FiloSottile/mkcert)를 쓰면 신뢰되는 로컬 인증서를 5분 안에 만들 수 있다.

```bash
# 로컬 CA 생성 + 시스템 신뢰 저장소 등록
brew install mkcert
mkcert -install

# 개발 호스트용 인증서 발급
mkcert -cert-file .certs/dev.pem -key-file .certs/dev-key.pem \
  app-local.example.com localhost 127.0.0.1
```

```ts
// vite.config.ts — 인증서가 있으면 https, 없으면 http로 기동
import fs from 'node:fs';

const https =
  fs.existsSync('.certs/dev.pem') && fs.existsSync('.certs/dev-key.pem')
    ? { cert: fs.readFileSync('.certs/dev.pem'), key: fs.readFileSync('.certs/dev-key.pem') }
    : undefined;

export default defineConfig({
  server: { https, strictPort: true },
});
```

인증서는 개발자마다 로컬에서 생성하고 커밋하지 않는다. 팀 문서에는 "인증서 없이 http로 뜨면 로그인이 성립하지 않는다"를 명시해두는 편이 좋다. 그리고 dev 서버의 CORS 허용 오리진도 `https://` 오리진으로 갱신해야 한다(함정 4에서 말했듯 CORS는 스킴까지 비교하므로, 스킴을 바꾸면 오리진도 다른 값이 된다).

검토할 수 있는 대안과 기각 사유:

- **쿠키를 `SameSite=None; Secure`로 완화** — 동작은 한다. 하지만 Lax가 공짜로 주던 CSRF 기본 방어선을 서비스 전체에서 포기하는 선택이다. 로컬 개발 편의를 위해 프로덕션 보안 속성을 낮추는 방향은 피하는 게 맞다.
- **전부 `http://localhost`로 통일** — 프론트·백엔드를 모두 로컬에서 띄우면 same-site라 동작한다. 배포된 API에 붙어야 하는 개발 흐름에서는 선택지가 못 된다.

부수 팁: hosts 파일로 매핑한 도메인(`127.0.0.1`)에 접속하려면 dev 서버가 IPv4에 바인딩돼 있어야 한다. Vite가 `localhost`(::1, IPv6)로만 리슨하면 hosts 도메인 접속이 connection refused가 된다 — `server.host: '127.0.0.1'`로 고정하면 해결된다.

## 7. 정리

- SameSite 쿠키는 CSRF를 막기 위해 "요청의 출발지"를 보기 시작한 방어선이고, 2020년부터 `Lax`가 기본값이다.
- site는 origin보다 느슨한 단위(eTLD+1)다 — 서브도메인 협력이라는 관행 때문에. 그러나 http가 same-site 자격을 가지면 네트워크 공격자가 그 느슨함을 뚫고 들어온다.
- 그래서 2021년부터 **site = (스킴, eTLD+1)**이 됐다. 스킴은 본다, 포트는 안 본다, 서브도메인은 묶는다.
- cross-site가 되는 순간 Lax 쿠키는 **저장과 전송이 모두** 차단된다. `withCredentials`는 이를 이기지 못한다.
- 실무 최대 함정은 http 로컬 개발 서버 ↔ https API 조합. 로그인만 성공해 보여서 원인을 엉뚱한 곳에서 찾게 된다.
- 해법은 스킴 통일 — mkcert면 로컬 https는 5분 거리다. 쿠키 속성 완화로 우회하지 말 것.
