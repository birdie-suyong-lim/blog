> 작성일: 2026-08-06
> 사내 백오피스 프로젝트의 세션 인증 연동 중 실제로 겪은 문제를 일반화해 정리했다.

로그인 API는 200을 돌려준다. 화면도 정상적으로 넘어간다. 그런데 그다음부터 이상해진다. 뭔가를 저장하려고 하면 CSRF 토큰 오류가 나고, 새로고침하면 로그인 화면으로 튕긴다. 다시 로그인하면 또 들어가진다. 그리고 또 실패한다.

이 글은 이 기묘한 증상의 범인이었던 **schemeful same-site** — SameSite 쿠키 판정에 스킴(http/https)이 포함된다는 규칙 — 을 정리한 것이다. 결론부터 말하면: **`http://` 페이지와 `https://` API는 같은 회사 도메인의 서브도메인끼리라도 cross-site다.** 그래서 `SameSite=Lax` 세션 쿠키가 저장도, 전송도 되지 않는다.

---

## 1. 증상: 반쯤 되는 로그인

환경은 흔한 구성이다. 로컬에서 프론트 개발 서버를 띄우고, 배포된 개발 서버 API에 붙는다.

- 프론트: `http://app-local.example.com:5173` (로컬 Vite dev 서버, hosts 파일로 127.0.0.1 매핑)
- API: `https://api-dev.example.com` (세션 쿠키 인증, `SameSite=Lax; Secure`)

`app-local.example.com`이라는 호스트를 쓰는 이유가 바로 SameSite 때문이다. `localhost`에서 API를 부르면 등록 도메인(eTLD+1)이 달라 cross-site가 되니까, 프론트도 같은 도메인 아래 서브도메인으로 접속하자는 설계다. 여기까지는 맞는 판단이다.

그런데 증상이 이랬다.

1. 로그인 → **200 성공**, 다음 화면으로 정상 이동
2. 폼 제출(POST) → **403 CSRF 토큰 오류**
3. 새로고침 → 세션 확인 API가 **401** → 로그인 화면으로 강제 이동
4. 다시 로그인하면 1번부터 반복

"로그인은 되는데"라는 사실이 디버깅을 완전히 잘못된 방향으로 끌고 갔다. 로그인이 됐으니 인증 자체는 정상이고, CSRF 토큰 처리 로직이나 계정 상태(잠금?) 문제라고 의심하게 된다. 실제로 우리도 계정 잠금 가설, CSRF 토큰 재발급 로직 가설, CORS 설정 가설을 차례로 세웠다 기각했다.

## 2. 결정적 관찰: 쿠키가 애초에 없다

전환점은 단순한 실험이었다. 로그인에 성공한 지 몇 분밖에 안 된 탭에서, 브라우저 콘솔로 세션 확인 API를 직접 호출해봤다.

```js
const r = await fetch('https://api-dev.example.com/api/v1/auth/me', {
  credentials: 'include',
});
r.status; // 401
```

**401.** 방금 로그인했는데 세션이 없다. `withCredentials`(axios) / `credentials: 'include'`(fetch) 설정도 확인했지만 정상이었다. "쿠키를 실어라"라는 지시는 하고 있는데 실리지 않는다면, 답은 하나다 — **브라우저가 쿠키를 저장한 적이 없다.**

DevTools > Application > Cookies에서 확인하면 실제로 API 도메인의 세션 쿠키가 보이지 않는다. 로그인 응답의 `Set-Cookie` 헤더는 분명히 내려왔는데도.

---

## 3. 원리: SameSite 판정에는 스킴이 들어간다

### "same-site"의 정의가 바뀌었다

원래 same-site 판정은 등록 가능 도메인(eTLD+1)만 비교했다. `a.example.com`과 `b.example.com`은 같은 `example.com` 아래이므로 same-site. 포트도 보지 않는다.

그런데 Chrome 89(2021년)부터 **Schemeful Same-Site**가 기본 적용되면서 정의가 바뀌었다. 이제 site는 **(스킴, eTLD+1) 쌍**이다.

| 페이지 | 요청 대상 | 판정 |
| --- | --- | --- |
| `https://a.example.com` | `https://b.example.com` | same-site |
| `http://a.example.com` | `https://b.example.com` | **cross-site** (스킴 불일치) |
| `https://a.example.com` | `https://localhost` | cross-site (eTLD+1 불일치) |

`http` 페이지에서 `https` API를 부르는 순간, 서브도메인이 같아도 cross-site다.

### cross-site가 되면 Lax 쿠키에 무슨 일이 일어나나

`SameSite=Lax` 쿠키는 cross-site 컨텍스트에서 두 가지가 모두 막힌다.

- **전송 차단**: cross-site XHR/fetch 요청에는 쿠키가 실리지 않는다.
- **저장 차단**: cross-site 응답의 `Set-Cookie`(Lax)는 브라우저가 저장을 거부한다.

즉 로그인 응답이 `Set-Cookie`를 내려줘도 브라우저가 버리고, 설령 저장돼 있어도 다음 요청에 싣지 않는다. 세션 인증이 성립할 방법이 없다.

### 왜 이 오개념이 생기나: Secure와 SameSite는 별개의 축이다

이 함정이 문서에까지 박제됐던 이유가 있다. 다음 명제는 **참**이다.

> 쿠키의 `Secure` 속성은 요청 대상이 https인지만 본다. API가 https라면 페이지가 http여도 `Secure` 쿠키는 전송될 수 있다.

여기서 "그러니까 페이지는 http여도 무방하다"는 **거짓** 결론으로 비약하기 쉽다. `Secure` 조건은 통과하지만, `SameSite` 판정이라는 **별개의 축**에서 스킴 불일치로 걸린다. 참인 전제에서 출발한 반쪽짜리 지식이라 오히려 더 위험하다 — 그럴듯해서 아무도 의심하지 않는다.

## 4. 왜 증상이 이렇게 교묘한가

이 문제의 진짜 악랄함은 **로그인이 성공해 보인다**는 데 있다.

- **로그인 요청은 쿠키가 필요 없다.** 자격증명은 요청 본문으로 가니까, 세션 쿠키 없이도 200이 떨어진다.
- **SPA는 로그인 응답만으로 화면을 전환한다.** 응답 본문의 세션 정보를 메모리에 들고 다음 화면으로 이동하므로, 쿠키가 버려진 걸 알아챌 계기가 없다.
- **처음 실패하는 요청은 로그인 다음 요청이다.** 그래서 문제가 "로그인 이후의 무언가"로 보인다.

보너스 함정도 있다. 서버 프레임워크에 따라(예: Spring Security) CSRF 검증 필터가 인증 확인보다 **앞**에 있어서, 세션 없는 POST 요청이 401(인증 필요)이 아니라 **403 CSRF 오류**로 떨어진다. "세션이 없다"는 본질이 "CSRF 토큰이 잘못됐다"는 엉뚱한 메시지로 위장되는 것이다. GET 요청이었다면 솔직하게 401이 났을 것을, POST라서 CSRF 에러가 된다 — 메서드에 따라 에러가 달라지니 더 헷갈린다.

## 5. 진단법: 30초 만에 확인하기

같은 증상을 만났을 때 바로 판별하는 순서.

1. **로그인 직후, 콘솔에서 세션 확인 API 호출**
   ```js
   await fetch('https://api-dev.example.com/api/v1/auth/me', { credentials: 'include' })
   ```
   방금 로그인했는데 401이면 쿠키 문제다. 토큰/CSRF 로직을 의심하기 전에 이것부터.
2. **DevTools > Application > Cookies** 에서 API 도메인의 세션 쿠키 존재 확인. 없으면 저장 자체가 거부된 것.
3. **주소창의 스킴 확인.** 페이지가 `http://`이고 API가 `https://`면 그게 범인이다.

## 6. 해법: 로컬 개발도 전 구간 https

근본 해결은 스킴을 맞추는 것뿐이다. 우리는 **로컬 개발 환경 전체(프론트·백엔드)를 https로 통일**하는 것으로 결론냈다.

프론트 dev 서버는 [mkcert](https://github.com/FiloSottile/mkcert)로 5분이면 https가 된다.

```bash
# 1) mkcert 설치 + 로컬 CA를 시스템 신뢰 저장소에 등록
brew install mkcert
mkcert -install

# 2) 개발용 호스트의 인증서 생성
mkcert -cert-file .certs/dev.pem -key-file .certs/dev-key.pem \
  app-local.example.com localhost 127.0.0.1
```

```ts
// vite.config.ts — 인증서가 있으면 https, 없으면 http로 뜨게
import fs from 'node:fs';

const https =
  fs.existsSync('.certs/dev.pem') && fs.existsSync('.certs/dev-key.pem')
    ? { cert: fs.readFileSync('.certs/dev.pem'), key: fs.readFileSync('.certs/dev-key.pem') }
    : undefined;

export default defineConfig({
  server: { https, strictPort: true },
});
```

인증서 파일은 개발자마다 생성하고 커밋하지 않는다(`.gitignore`에 인증서 폴더 등록). 팀 문서에는 "인증서가 없으면 http로 뜨지만 그 상태로는 로그인이 성립하지 않는다"를 명시해두는 게 좋다.

검토했지만 선택하지 않은 대안:

- **`SameSite=None; Secure`로 완화** — 쿠키는 동작하지만, Lax가 제공하던 CSRF 기본 방어선을 포기하는 것이라 로컬 편의를 위해 보안 속성을 바꾸는 방향은 피했다.
- **`http://localhost` 조합으로 회귀** — 프론트·백엔드 모두 localhost면 same-site라 동작한다. 다만 배포 환경 API에 붙어야 하는 개발 흐름에서는 선택지가 못 된다.

부수 팁 하나: hosts 파일로 매핑한 도메인(`127.0.0.1`)으로 접속하려면 dev 서버가 IPv4에 바인딩돼 있어야 한다. Vite가 `localhost`(::1, IPv6)로만 리슨하면 hosts 도메인 접속이 connection refused로 거부된다 — `server.host: '127.0.0.1'`로 고정하면 해결된다.

## 7. 정리

- **same-site 판정은 (스킴, eTLD+1) 기준이다.** 포트는 안 보지만 스킴은 본다. http 페이지 ↔ https API는 같은 도메인이라도 cross-site.
- cross-site에서 `SameSite=Lax` 쿠키는 **저장과 전송이 모두 차단**된다. 로그인 응답의 Set-Cookie가 조용히 버려진다.
- 로그인 요청 자체는 쿠키가 필요 없어 **성공해 보이는 것**이 이 문제의 위장술이다. 첫 진단은 "로그인 직후 세션 확인 API가 401인가"로 시작하라.
- `Secure`와 `SameSite`는 별개의 축이다. "API가 https니까 페이지는 http여도 된다"는 반쪽 지식을 조심할 것.
- 해법은 스킴 통일 — mkcert면 로컬 https는 5분 거리다.

같은 증상으로 헤매는 누군가의 디버깅 시간이 하루쯤 줄었으면 한다.
